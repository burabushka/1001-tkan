# Landing Design MD

Универсальный дизайн-док для создания любого лендинга компании. Используется перед Figma, HTML-прототипом или разработкой.

## 1. Приоритеты

1. Брендбук компании — главный источник истины: логотип, цвета, шрифты, тон, ограничения.
2. Бизнес-цель лендинга — важнее декоративной идеи.
3. Контекст продукта и аудитории — определяет структуру, оффер и CTA.
4. Референсы — только источник композиции и приемов, не источник бренда.
5. Тренды UI — использовать только если они усиливают конверсию и доверие.

Если брендбук конфликтует с референсом, побеждает брендбук.

## 2. Входные данные

Перед дизайном собрать:

- компания и продукт;
- аудитория: кто покупает, зачем, с какими страхами;
- целевое действие: заявка, звонок, покупка, регистрация, бронь;
- основной оффер в 1 фразе;
- 3-5 доказательств: опыт, цифры, кейсы, отзывы, гарантии;
- ограничения: брендбук, CMS, сроки, юридические требования;
- список обязательных блоков;
- источники контента: фото, видео, каталог, документы, отзывы.

## 3. Базовый промт

```text
Создай лендинг для компании [COMPANY].

Цель: [PRIMARY_ACTION].
Аудитория: [AUDIENCE].
Оффер: [OFFER].
Главные доказательства: [PROOFS].
Тон: [TONE].

Дизайн строить по брендбуку: использовать фирменные цвета, шрифты, радиусы, стиль изображений и ограничения бренда.
Референсы использовать только для композиции, ритма, плотности и UI-паттернов.

Лендинг должен быстро объяснять ценность, снимать возражения, показывать доверие и вести к одному главному действию.
```

## 4. Структура лендинга

Обязательный минимум:

1. Header  
   Логотип, навигация по якорям, контакт/CTA. Sticky, если страница длинная.

2. Hero  
   H1 = конкретный оффер, не абстрактный слоган.  
   Подзаголовок = кому, что, какой результат.  
   1 primary CTA + 1 secondary CTA.  
   3 коротких буллита под CTA: наличие/срок/выгода/гарантия.

3. Problem / Context  
   Показать ситуацию пользователя и почему текущее решение неудобно.

4. Solution  
   Как компания решает задачу. Лучше через процесс, продукт или пакет услуг.

5. Proof  
   Цифры, клиенты, кейсы, отзывы, сертификаты, физическое наличие, опыт.

6. Product / Service Details  
   Карточки услуг, товаров, тарифов или сценариев применения.

7. Process  
   3-5 шагов: заявка → подбор → согласование → оплата → результат.

8. Lead Form / Calculator  
   Минимум полей. Поля только те, которые реально нужны для первого ответа.

9. FAQ  
   Возражения: цена, сроки, доставка, гарантия, документы, возврат, безопасность.

10. Final CTA  
   Повтор оффера, короткая форма или кнопка.

11. Footer  
   Реквизиты, контакты, ссылки, юридическая информация.

## 5. Сетка и layout

Desktop:
- 12 колонок;
- max-width 1200-1440px;
- gap 20-32px;
- секции с вертикальным rhythm 80-140px;
- hero занимает первый экран, но должен показывать намек следующего блока.

Tablet:
- 8 колонок или адаптивная 12-column сетка;
- карточки 2 в ряд;
- hero чаще складывается в 1 колонку.

Mobile:
- 4 колонки или single-column;
- CTA виден без скролла;
- карточки идут вертикально;
- меню компактное;
- формы без мелких полей в ряд.

## 6. Цветовая система

Цвета брать из брендбука.

Минимальный набор токенов:

```css
--color-bg: #FFFFFF;
--color-surface: ...;
--color-text: ...;
--color-muted: ...;
--color-border: ...;
--color-primary: ...;
--color-primary-hover: ...;
--color-secondary: ...;
--color-success: ...;
--color-warning: ...;
--color-danger: ...;
```

Правила:
- primary использовать только для главных CTA и активных состояний;
- muted — для вторичного текста, но не для важных условий;
- dark blocks — только для сильного смыслового акцента;
- не создавать новую палитру из референса, если есть брендбук;
- проверять контраст кнопок и текста.

## 7. Типографика

Минимальная шкала:

| Роль | Desktop | Mobile |
|---|---:|---:|
| H1 | 56-72px | 38-48px |
| H2 | 40-52px | 30-36px |
| H3 | 24-32px | 22-26px |
| Card title | 18-22px | 17-20px |
| Body | 16-18px | 15-16px |
| Caption | 12-14px | 12-13px |

Правила:
- не масштабировать шрифт от ширины viewport;
- `letter-spacing: 0`, если брендбук не требует иначе;
- заголовки должны быть короткими;
- в карточках не использовать hero-size типографику;
- кнопки и формы должны читаться на мобильном.

## 8. UI-компоненты

Обязательные компоненты:

- Header / Nav;
- Button primary;
- Button secondary;
- Text link;
- Card;
- Feature card;
- Stat card;
- Testimonial card;
- Input;
- Select;
- Textarea;
- Tabs;
- Accordion;
- Badge / Pill;
- Alert / Status;
- Footer.

Для каждого компонента задать:
- default;
- hover;
- focus;
- active;
- disabled;
- loading, если есть отправка формы.

## 9. Изображения

Правила:
- изображения должны показывать реальный продукт, услугу, результат или процесс;
- не использовать темные, размытые, случайные stock-фото;
- текст не должен быть вшит в изображение;
- CTA и важные смыслы — HTML/UI;
- задать стабильные пропорции: `aspect-ratio`, `object-fit`, min/max размеры.

Типовые пропорции:
- hero/banner: `16 / 7`, `16 / 9` или full-bleed;
- product card: `3 / 4`, `4 / 5`, `1 / 1`;
- case/testimonial image: `4 / 3`;
- avatar/logo: square/circle.

## 10. Контент и UX

Писать конкретно:
- не «лучшее качество», а «отгрузка за 24 часа»;
- не «индивидуальный подход», а «менеджер подберет 3 варианта за 10 минут»;
- не «выгодные цены», а «скидка 37% от одного рулона».

Каждый блок должен отвечать на один вопрос:
- что это?
- кому подходит?
- почему верить?
- что делать дальше?

CTA:
- на первом экране;
- после доказательств;
- рядом с формой;
- в финальном блоке.

## 11. Формы

Форма должна быть короче, чем желание пользователя уйти.

Правила:
- 3-5 полей максимум для первого контакта;
- обязательные поля явно отмечены;
- ошибки рядом с полем;
- успешная отправка с понятным следующим шагом;
- телефон/email не маскировать так, чтобы мешать вставке;
- если форма длинная — разбить на шаги.

## 12. Доверие

Использовать реальные доказательства:
- годы на рынке;
- количество клиентов/заказов;
- физические адреса;
- фото команды/склада/процесса;
- документы;
- отзывы с именем и ролью;
- кейсы с результатом;
- гарантии и условия возврата.

Не использовать абстрактные бейджи без смысла.

## 13. Адаптив и доступность

Проверить:
- нет горизонтального скролла;
- CTA видим и нажимаем;
- tap target не меньше 44px;
- focus state виден;
- контраст текста достаточный;
- accordion/tabs доступны с клавиатуры;
- изображения имеют alt;
- порядок заголовков логичный;
- формы имеют label.

## 14. Технические правила для HTML/Tailwind

- Один главный контейнер на секцию.
- Сетка: `grid-cols-12` на desktop, аккуратный collapse на mobile.
- Повторяющиеся элементы делать одинаковыми по размеру.
- Не вкладывать карточки в карточки без необходимости.
- Не использовать декоративные blob/orb-фоны.
- Не делать landing похожим на маркетинговую презентацию, если продукт операционный/B2B.
- Для интерактива достаточно Vanilla JS: tabs, accordion, menu, form states.

## 15. Acceptance checklist

Лендинг готов, если:

- H1 объясняет оффер за 5 секунд;
- первый экран содержит CTA и 3 доказательства;
- структура ведет от ценности к доверию и действию;
- брендбук соблюден;
- цвета не взяты слепо из референса;
- все изображения имеют заданные пропорции;
- mobile не ломается;
- формы и FAQ работают;
- нет переполнения текста;
- CTA повторяется в ключевых местах;
- есть понятный финальный следующий шаг.

## 16. Быстрый шаблон секций

```text
Header
Hero
Bullets
Problem
Solution
Proof / Metrics
Services / Products
Process
Cases / Reviews
Calculator / Form
FAQ
Final CTA
Footer
```

## 17. Что нельзя

- Начинать дизайн с красивой картинки вместо оффера.
- Делать H1 рекламным лозунгом без конкретики.
- Использовать больше 1 главного CTA.
- Смешивать разные визуальные стили на одной странице.
- Игнорировать брендбук ради референса.
- Прятать цену, сроки или условия, если это главное возражение.
- Делать форму длинной без причины.
- Оставлять важный текст только на изображении.
